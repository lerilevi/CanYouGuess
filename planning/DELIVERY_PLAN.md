## Changes to the original roadmap

1. Move an independent review of the question/session contract and unit economics ahead of the bulk of client integration. A defective contract or unsustainable promise of lifetime unlimited AI can change what we need to build. Keep a second, complete quality audit after integration, using the actual target backend and generated output.
2. Move observability and repeatable testing earlier. Add Sentry, EAS Update, and a reusable iPhone development client before a long feature-fix cycle. A development build and a store build are separate compilations and consume two iOS slots even when they share the same native changes.
3. Separate reliability, monetization correctness, and game quality gates. A purchase sheet opening does not prove fulfillment, restoration, or identity isolation. A client counter reaching 15 does not prove the backend prevents bypasses. A matching JSON schema does not prove a factual answer is correct.
4. Do not wire the v2 drafts unchanged. `profileService.v2.ts` still calls `submit_score` and `award_badge`; the current migration set exposes the authoritative question-session finalization flow instead. Its comment that the device is the authority for the date is also obsolete. The migration runbook explicitly flags these drafts as predating the authoritative flow.
5. Add a data/identity cutover plan. The user has now approved an empty beta reset; no real user/score/purchase preservation is required. Supabase project changes still affect persisted sessions and RevenueCat user IDs. Reset old-project sessions/test caches deliberately; changing a URL alone is insufficient. Project deletion is not authorized.
6. Add the missing backend monetization work explicitly: authoritative entitlement lookup/synchronization, verified rewarded-ad transactions, atomic allowance/credit reservations, deduplication, refund/revocation handling, and reconciliation after delayed events. The current backend's AI abuse limits are not product allowances; the target has no daily rewarded product cap.
7. Correct the SDK item. The app is already on Expo SDK 53 / React Native 0.79.3 with the old architecture enabled. A future SDK upgrade needs its own compatibility and architecture decision. Do not mix it with baseline confirmation or broad dependency pruning.
8. Treat broad pruning as a separate optional native change. The package list is large, but removal requires an import/config/platform inventory. A dependency not imported by one screen may still be used by a plugin or another platform. The integration merge must not resurrect expo-calendar or older build configuration.
9. Choose a small external beta by default once the safety gates pass. It is not necessary to perfect every proposed feature before collecting feedback. SMTP, account deletion, safe money handling, adequate privacy, backend access controls, and usable crash reporting are prerequisites.
10. Replace blanket end-of-task revocation with a credential inventory. Revoke exposed/obsolete credentials and temporary administrative tokens. Retain narrowly scoped deployment/upload credentials that ongoing builds and services need, in their proper secret stores. SMTP and server-side Gemini credentials are persistent runtime dependencies. Supabase publishable keys, RevenueCat public SDK keys, and Sentry DSNs are public client configuration; they are not privileged secrets.

## Crash reporting choice

**Recommend Sentry for this app.** The primary engineering need is readable React Native/Hermes JS errors alongside native failures, release/update identity, and breadcrumbs. Expo documents its EAS Build and Update source-map workflow. Crashlytics is reasonable if we already use Firebase and prioritize its ecosystem; here it would add Firebase core as well as Crashlytics. Pin a version verified against SDK 53, RN 0.79 and the existing architecture rather than installing a latest major blindly. [Expo/Sentry guide](https://docs.expo.dev/guides/using-sentry/), [React Native Firebase Crashlytics](https://rnfirebase.io/crashlytics/usage)

Start with errors/crashes, minimal non-sensitive breadcrumbs and conservative quotas; defer session replay and broad performance telemetry. Initialize early enough to capture route import failures while preserving and deliberately testing the existing handlers and RCTFatal behavior. Avoid double-reporting and avoid changing fatal behavior accidentally. A JS boundary test does not prove native crash reporting: verify a native test crash separately in a tester-only build/flag, relaunch to send it, and inspect a symbolicated report. Remove public crash-trigger routes before external beta. Log version, build number, git commit, environment, and OTA update ID; redact tokens, email addresses and raw user answers.

Needed: Sentry organization/project, DSN, desired data region, alert recipient, and a narrowly scoped source-map/release upload token stored in build/CI secrets. Keep that upload credential while the release pipeline uses it.

Installing SMTP does not itself fix OTP length, templates, recovery routing or email-change verification. [Supabase SMTP](https://supabase.com/docs/guides/auth/auth-smtp)

**Recommend Resend as the simplest initial choice**, unless an approved transactional email provider is already available. SES is reasonable if an existing AWS/domain setup makes its operational work cheaper. Choose an owned sender domain or subdomain; GitHub Pages hosting does not provide sender-domain verification. Resend documents a verified domain and SMTP setup for Supabase. [Resend/Supabase SMTP](https://resend.com/docs/send-with-supabase-smtp)

Specific purchase recommendation: standard `canyouguessapp.com`, one year through Cloudflare Registrar; published .com registration/renewal is currently US$10.46 before applicable checkout taxes. A registry check found no registered record on October 4; checkout is definitive. No paid hosting/mailbox is required to send auth emails. Verify `auth.canyouguessapp.com` in Resend; the setup guide gives the expected DKIM, bounce MX/SPF and initial DMARC records. The generated key and regional hostname must come from the actual provider panel. [Registrar price](https://pricing.registrar.cloudflare.com/)

The existing Gmail address works as a support contact. Consumer Gmail SMTP is a conditional tiny invite-only stopgap using 2FA/app passwords, not the recommendation for open beta. Supabase's documented SMTP UI does not have a separate Reply-To field; a support template link is straightforward, while real Gmail reply routing needs a tested forwarding or email-hook solution. Do not promise a nonexistent checkbox. [Google app passwords](https://support.google.com/accounts/answer/185833), [email hook](https://supabase.com/docs/guides/auth/auth-hooks/send-email-hook)

Needed: domain and DNS access (or someone to publish records), provider account, sender name/address, reply-to/support mailbox, expected signup volume, and permission/access to the target Supabase Auth configuration. Store SMTP host/port/username/password in the Supabase SMTP settings; do not put the SMTP password in mobile/EAS public configuration or in chat. For Resend, the SMTP password is the provider key. Verify DKIM/SPF, choose a DMARC policy, disable email click rewriting where it interferes with auth links, and set sensible Supabase/provider rate limits and abuse controls.

Verification: deliver signup, recovery, and email-change messages to independent non-team addresses (at least two mailbox providers); complete the real device flows. Prefer matching the UI to the configured default six-digit email OTP rather than reducing the OTP to fit an old four-box UI. Test resend/expiry, wrong and reused codes, recovery links while logged out and while running, and links that expire. Keep email confirmation enabled.

## Functional gates that were missing or understated

- Define what consumes an allowance: generated question, answered question, or reserved session. Unanswered generation still incurs AI cost. Reserve atomically, limit concurrent outstanding sessions, deduplicate retries and refund failed requests according to a documented rule. A UI failure must not create extra charges or scores.
- Use the server's time plus a validated user timezone; decide how timezone changes affect allowances. A once-per-launch update alone does not prevent repeated resets. Define a shared competition window for daily/weekly leaderboards instead of assuming per-user day windows are directly comparable.
- Keep correct answers behind the server until evaluation. Verify real JWTs and cross-user access, replay/concurrency, stale requests, rate limits, cache poisoning and malformed AI output; rerun hosted authorization smoke tests as well as pgTAP.
- Build a single reachable limit/paywall/reward path for all entry points, including Categories and retry. Approved target: one server-verified ad grants one bonus; no daily product cap. Server-configure reward value, cooldown and separate technical ceilings. The signed callback grants credit atomically; the SDK callback only shows pending until verification. No-fill grants nothing and consumes nothing. See the detailed contract for duplicate, delayed and account-switch cases.
- Verify AdMob SSV, authenticated/deduplicated transaction handling and delayed reward UX. UMP must refresh consent and gate requests appropriately; ATT denial is not the same as denying all ads. The existing AdsConsent wrapper already provides UMP APIs, but SDK measurement/config changes may still require a native build. Use registered test devices/test ads before live units. [UMP](https://developers.google.com/admob/ios/privacy), [reward verification](https://developers.google.com/admob/ios/ssv)
- For RevenueCat, coordinate SDK initialization and app identity, update on customer-info changes, show a loading/unknown state rather than treating a lookup failure as free, and verify purchase/restore/logout/account-switch/reinstall/refund cases. Use authenticated backend synchronization and reconciliation for delayed webhooks; separate sandbox event handling from production. Confirm the account's integration entitlement before depending on webhooks. [RevenueCat webhooks](https://www.revenuecat.com/docs/integrations/webhooks)
- Publish legal/support pages before public testing; map actual data flows, include AI-sharing permission where applicable, and match App Privacy disclosures to the shipped SDKs. Proposed reach is English-literate players across eligible countries; age and username moderation remain unresolved. Existing draft Terms still promise unlimited questions and are blocked pending economics/copy approval. Include accessible text sizes/VoiceOver, slow/offline networks, background/resume, and iPad layout because the current app declares tablet support. [Apple review guidelines](https://developer.apple.com/app-store/review/guidelines/)

Ranked competition is a separate contract decision, not summed unlimited practice. Proposed design: one fixed daily challenge with equal free/paid/ad-funded opportunities; shared UTC daily periods; Monday-to-Monday weekly mean of seven daily results (missing days zero); qualified lifetime mean within one comparable rules version for all-time. No best-N cherry-picking, rerolls or extra ranked attempts from ads. Initial K=10 and 20-day all-time qualification are proposals to simulate, not approved values. Decide whether ranked questions reserve part of the 15 free or have a separately costed allowance; spending free practice must not force a purchase/ad to enter competition. Global versus country-specific pack comparability also needs review. See the contract document for the raw-SUM/local-window code finding and boundary tests.

The original feature checklist and carry-over bug list remain acceptance inputs, not completed work. In particular: signup username persistence, OTP UI, password recovery, country/local leaderboard behavior, Categories allowance/consent bypass, numeric result formatting, retry country preservation, filter races, malformed AI output, country-lookup timeout/redundancy, and dead guest-mode paths need explicit tests and dispositions. Before external beta, also verify review-account access, restore-purchase UI, the first IAP's App Store submission linkage, current age/privacy declarations, encryption declaration, support URLs, and the privacy manifest/purpose strings for the SDKs actually shipped. If Android is chosen, research the account-specific Play testing requirements then; do not reuse the iOS estimate as an Android schedule.

Security housekeeping is separate from build 19: inventory the administrative App Store key reported in a OneDrive-synced directory, move required key material to an approved non-synced secret store and rotate if exposure warrants it. ## Independent audit protocol

Before requesting or reading another reviewer's notes, I will freeze the audited commit and deployed backend/model configuration, inspect the real game/question/scoring code, run real generation/evaluation, and write my own findings with severity and reproducible evidence. Only after that written record exists will we compare external findings. This planning review is not the game-quality audit, and no synthetic example will be presented as actual generated evidence.

Produce raw UTF-8 JSONL plus a readable text/Markdown report. Each record includes category, difficulty, country context, exact question/hint, the server-held accepted answer/reference value when available, submitted answer, actual score, actual explanation, session/request IDs, model/prompt/function version, latency, token/cost data when returned, and errors. Use disposable test identities and preserve secrets/PII redaction. Snapshot server-held trivia answers in a restricted test export before evaluation deletes them; never relax client answer secrecy to collect samples.

Start with a small balanced pilot (for example two questions per category/difficulty cell), write initial independent findings, then expand to ten per cell if the pilot and approved AI spending justify it. With seven categories and three difficulties, ten per cell is 210 questions, plus evaluations and deliberate edge-case runs; it is not a small free test. Verify the actual category/difficulty inventory first. Agree an AI request/cost cap before that expansion. Use fresh sessions for alternate guesses because a finalized session must not be scored twice.

Assess factual correctness using independently checked references, ambiguity, units, aliases/numeric formats, duplicates, country accuracy, difficulty and coverage; measure score/explanation consistency and numeric fairness; test input/adversarial boundaries and exploits; assess onboarding, pacing, accessibility and economics. Report factual defects separately from subjective game-design proposals. Do not rewrite scoring or the pricing promise merely to match another reviewer's opinion.
